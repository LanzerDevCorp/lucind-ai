# Meta-Harness Landscape — Research Dossier

Research date: 2026-08-14. Scope: orchestrators over agent CLIs ("meta-harnesses"), agent-to-agent protocols, multi-model routing by aptitude, and observability for opaque CLI processes — bounded to the six questions below, in support of the `lucind-ai` orchestration design (orchestrator + `agy` execution lane + `opencode` audit lane + human secret lane + verifiable result envelopes).

Method note: every claim below was checked against a fetched primary source (raw READMEs, docs files, GitHub Releases pages, spec files, protocol sites) rather than search-result summaries, except where explicitly marked **[unverified]**. Search-engine AI summaries were used only to find candidates, never as evidence themselves — every candidate that made it into a table row was independently fetched.

## Executive Summary

1. **Correct the starting premise**: Omnigent *does* list Antigravity — `harness: antigravity` (aliases `agy`, `google-antigravity`) is documented in `docs/AGENT_YAML_SPEC.md`, and the GitHub Releases changelog shows a shipped feature "sign in to Antigravity with Google OAuth via `agy`" plus "add `agy` as a Polly sub-agent." The premise that Omnigent has no Antigravity path is out of date.
2. **But the two Antigravity paths are not equivalent.** The YAML-spec example authenticates with `auth: {type: api_key, api_key: ${GEMINI_API_KEY}}` — a per-token API key, economically dead for a subscription-only setup. The OAuth-via-`agy` path (changelog only, not confirmed in the spec doc as fetched) is the one that could be subscription-compatible, but its authentication surface and session-driving mechanism are not documented in the files this research could reach. This is the single most important unresolved item — see Open Questions.
3. **CAO is the only orchestrator with a *documented, working* subscription-auth Antigravity integration.** It drives `agy`'s interactive TUI by screen-scraping tmux panes through a `pyte`-based FIFO pipeline, classifying agent state from a footer-anchored, render-stable status region — not by calling any SDK or API.
4. **Omnigent already has the infrastructure CAO uses for Antigravity** — `tests/harness_bench/test_native_tui_driver.py` — meaning Omnigent's own test bench already exercises a native-TUI-driving code path. Whether that path is wired to the `antigravity` harness id specifically is unverified from the docs alone; it would need direct code inspection, not just doc/README reading.
5. **Cross-vendor agent-to-agent communication is real but not vendor-native.** Claude Code shipped native intra-vendor session messaging (`ListAgents`/`SendMessage`, Claude Code 2.1.224, Aug 7 2026). A Claude Code ↔ Codex bidirectional bridge exists only as an individual developer's 24-hour proof-of-concept (`openai/codex` Discussion #15374), explicitly challenged by another practitioner in the same thread as not really "one session." MCP is the practical cross-vendor bridge today — both CLIs act as MCP client *and* server — but no vendor ships a first-party cross-vendor session bridge.
6. **ACP (Agent Client Protocol) is Omnigent's actual harness-extension mechanism**, not a bespoke driver-per-CLI model. Grok Build (xAI) shipped as "a first-class ACP harness," and Omnigent's OpenClaw integration drives "each agent's ACP command directly" or bridges a live OpenClaw Gateway over ACP. If `agy` ever exposes an ACP server, that is the more durable integration path than a bespoke TUI driver.
7. **Cursor Router is the closest thing to a published aptitude-routing architecture**, and it validates the "cheap-fast-generator + selective-upgrade" shape the user's aptitude map assumes: a "Compass" complexity classifier scores each turn 0–1 and a tunable threshold decides whether it stays on the cheap model or upgrades to a frontier model — this is architecturally the same shape as generate-fast/verify-strict, but Cursor's public writeup does not publish per-model aptitude breakdowns (which model wins at what task type). The user's aptitude map is **plausible but not directly validated** by any primary source found.
8. **The observability trap is real and independently confirmed**: a Langfuse GitHub discussion (`langfuse/langfuse` Discussion #13542) states explicitly that `claude-agent-sdk` is "a thin wrapper around the `claude` CLI binary" and that Langfuse "cannot see into this subprocess" — the exact failure mode `lucind-ai` was designed around.
9. **All four `lucind-ai` primitives remain genuinely differentiated.** No harness found ships a schema-verified result envelope with mandatory hard-stop declaration as a first-class contract; Omnigent's closest analog (policy ALLOW/DENY/ASK verdicts) is a pre-action gate, not a post-hoc verifiable receipt. None ship a dedicated "never let an agent see a secret" lane as opposed to an approval pause. A durable task ledger exists in Gas Town (convoys/beads) but is coupled to its own tmux/Go runtime, not to `agy`.
10. **Maturity note**: Omnigent moves fast (v0.3.0 → v0.6.0 → v0.9.0 across roughly seven weeks, 8.8k stars, Apache-2.0, alpha) and is the best architectural fit overall, but "alpha" is accurate — breaking CLI changes appear release-to-release (e.g., `omni server start` → `omni server --background`).

## Q2. The Antigravity Gap

**(a) Omnigent's documented extension path for a new harness.**

- `docs/AGENT_YAML_SPEC.md` treats `harness:` as an open enum: `claude-sdk, openai-agents, codex, cursor, kiro-native, pi, antigravity, qwen, kimi, copilot, hermes, ...` — the trailing `...` and the doc's own instruction ("Adding or changing support for a harness ... run the harness test bench") show harnesses are meant to be added, not a closed list.
- `tests/harness_bench/` contains `test_bench.py`, `test_cost_tracking.py`, `test_fork_replay.py`, `test_full_server.py`, `test_full_server_driver.py`, and **`test_native_tui_driver.py`** — the presence of a "native TUI driver" test file is direct evidence Omnigent has (or is building) the exact capability CAO uses for `agy`: driving an interactive full-screen TUI CLI, not just an API/SDK. This file was located by directory listing (`tests/harness_bench` tree view); its contents were not read line-by-line, so the claim is "the file exists and its name implies this capability," not "the code was inspected."
- `CONTRIBUTING.md` confirms the general contribution path (open an issue first for large changes) but has no harness-specific section beyond the pointer already in the README.

**(b) How CAO integrates Antigravity CLI, and what interface it requires.**

From `docs/antigravity-cli.md` (fetched directly):
- Requires the **tmux** backend (`cao-server --terminal tmux`, the default).
- Opts into `supports_screen_detection = True`, driven by "the FIFO / pyte pipeline that tmux provides" — i.e., CAO reads the rendered terminal screen (via `pyte`, a terminal emulator library) off a tmux pane, not any API.
- Classifies `agy` states "from the tmux output buffer (footer-anchored, render-stable)" — meaning the interface contract CAO needs from a CLI is: a TUI with a *stable, parseable status region* it can poll via terminal-screen diffing.
- MCP integration: `agy` reads MCP servers from `~/.gemini/config/mcp_config.json` (legacy Gemini CLI path — confirms `agy` is architecturally the Gemini CLI's successor, consistent with the "Google retired the free Gemini Code Assist path (2026-06-18)" framing in the same doc). CAO merges its own MCP server entry into that file at launch and forwards a `CAO_TERMINAL_ID` env var so its MCP server can resolve which terminal a handoff/assign call came from.
- **The interface CAO requires of any CLI, generalized**: (1) launchable non-interactively into a persistent terminal session, (2) a screen region whose renders are stable enough to regex/pattern-match for state, (3) an MCP-config file CAO can inject its own server into. This is a comparatively low bar — no vendor cooperation required, which is exactly why CAO could add Antigravity support without an Antigravity-side SDK.

**(c) Evidence of Omnigent + Antigravity discussion/work.**

- The GitHub issue search UI for "antigravity" in `omnigent-ai/omnigent` did not return distinct, extractable issue content through the fetch used (search results page rendered without individual issue rows visible in the fetched markdown) — **inconclusive**, not "no issues exist."
- Stronger and more direct evidence came from the **Releases changelog**, which is a primary source: an entry reading "🔌 More agents and sign-ins: sign in to Antigravity with Google OAuth via `agy`, import OpenClaw/acpx coding agents into the ACP picker (`omnigent run --from-openclaw`), add `agy` as a Polly sub-agent, and launch Claude/Codex children in goal mode" appears in the fetched releases page. This is unambiguous proof that Antigravity/`agy` support **shipped**, contradicting the "does not list Antigravity" premise as stated. The exact version tag this entry belongs to was not pinned precisely (releases page showed v0.3.0, v0.6.0, and v0.9.0 as sequential tags in the same feed; the OAuth entry sits among "Major new features" text not tied to a single visible tag in the excerpt captured) — **treat the fact of shipping as confirmed, the exact version as unverified**.
- Net assessment: **the "Antigravity gap" as originally framed (Omnigent has no Antigravity path) is factually outdated.** The live gap is narrower and different: whether Omnigent's OAuth-via-`agy` sign-in actually drives the subscription CLI session (CAO's model) versus routing through Google's API surface under the hood (economically different even with OAuth, if it consumes API quota rather than the flat-rate CLI entitlement). That distinction could not be resolved from documentation alone.

## Q4. Multi-Model Routing by Aptitude

- **Cost-based routing research is mature and well-benchmarked**: RouteLLM (arXiv:2406.18665, "Learning to Route LLMs with Preference Data") routes simple queries to a weak/cheap model and reserves a strong model for complex queries, reporting >2x cost reduction without quality loss in some evaluations. Follow-on benchmarks exist to evaluate routers themselves: RouterBench (405k+ precomputed outputs across 11 models/7 tasks: MMLU, MT-Bench, MBPP, HellaSwag, Winogrande, GSM8K, ARC), RouterEval (200M+ records, 8,500+ models, 12 benchmarks), LLMRouterBench (400K+ instances, 21 datasets, 33 models). These are quality-vs-cost routers, not per-task-type aptitude routers — they answer "how strong a model do I need," not "which vendor's model is best at this *kind* of task."
- **Generator/verifier and mixture-of-model architectures have direct academic grounding**: Mixture-of-Agents (arXiv:2406.04692, "Mixture-of-Agents Enhances Large Language Model Capabilities," Wang et al.) is a layered proposer/aggregator architecture where multiple LLMs each generate a response and another LLM synthesizes/refines across them — structurally close to a generate-then-verify pattern, though MoA is about response quality via aggregation, not specifically a cheap-generator + expensive-strict-verifier split.
- **The closest production evidence of the user's exact "generate-fast, verify-strict" architecture pattern**: **Cursor Router**, launched 2026-07-22 (per Cursor's own blog, fetched directly). It uses a "Compass" complexity classifier that scores each turn 0–1 for complexity and applies a tunable threshold: below threshold, stay on a price-efficient model ("Composer"); above threshold, upgrade to a frontier model. This is architecturally the fast-cheap-generator-with-selective-escalation pattern the user's design assumes, and it is in production, not a paper. However, Cursor's public writeup reports aggregate cost/satisfaction curves relative to Opus 4.8, **not** a breakdown of which specific model (Grok, Gemini, GPT, Claude) wins at which task category — so it validates the *shape* of the architecture, not the specific claim "Gemini is fast/error-prone, Grok is a good fast-mid-size performer."
- **Validating/challenging the user's aptitude map directly**: No primary source found that benchmarks Claude/GPT/Cursor+Grok/Gemini specifically on the axes the user cares about (judgment/architecture vs. strict validation vs. fast-mid-size vs. cheap-but-error-prone-generator). Aggregate leaderboard data gathered via search (SWE-bench Verified/Pro, DeepSWE v1.1) shows Claude models leading most 2026 coding leaderboards, with figures like "Claude Fable 5's SWE-bench Verified is 95.0%" explicitly caveated by the source itself as "single-sourced and unconfirmed directly by Anthropic" — **do not treat these numbers as verified**; several of the sourcing sites (smartscope.blog, felloai.com, tech-insider.org, lmcouncil.ai) read as SEO/aggregator content rather than primary benchmark publishers and were not independently fetched/verified in this research pass.
- **Net**: the user's aptitude map is a reasonable, production-precedented *shape* (Cursor Router proves the shape works and ships), but the specific per-vendor aptitude assignments (Claude=judgment, GPT=strict audit, Grok=fast-mid, Gemini=fast-but-error-prone) are **not directly validated by any benchmark found** — they should be treated as the user's working hypothesis, testable via their own generate-and-verify loop, not as externally proven fact.

**Bottom line for Q5**: the field has converged on exactly two workable patterns for opaque-CLI observability — **(1) hook-based instrumentation**, when the CLI vendor ships hooks (Claude Code confirmed rich and stable; Codex's hook system exists but its exact shipped status is less certain from what could be verified), and **(2) tmux/pty screen-scraping**, which works on literally any interactive CLI regardless of vendor cooperation and is already production-proven by CAO and Gas Town. Framework-wrapping tools (Langfuse/LangSmith/Arize) are confirmed, by the vendors' own community discussion, not to solve this problem for CLI subprocesses.

## Q6. Gap Analysis

| `lucind-ai` primitive | Provided by any harness found? | Verdict |
|---|---|---|
| **1. Verifiable result envelope with schema** | Not found as a first-class, schema-validated contract anywhere surveyed. Omnigent's policy engine produces ALLOW/DENY/ASK *verdicts* at action time (pre-hoc gating), not a structured, schema-checked *result* the caller can validate post-hoc. Hermes's "typed result objects" are the closest conceptual cousin (structured, not raw text, passed orchestrator-ward) but no JSON Schema or equivalent contract was found documented. | **Keep building — no harness provides this.** |
| **2. Mandatory hard-stop declaration (undeclared hard-stop invalidates an otherwise-green result)** | Nothing found does this. Policy engines (Omnigent) and escalation docs (Gas Town) handle *pausing before an action*, not *invalidating a completed result if a stop condition wasn't explicitly declared*. This is a distinctly stricter, audit-oriented contract than anything surveyed. | **Keep building — genuinely novel among surveyed tools.** |
| **3. Human lane for secrets (no agent ever writes a credential value)** | The closest analog is Omnigent's `ask` policy verdict (pause for user approval before a shell/file-write action) — but that is a generic approval gate, not a secrets-specific lane that structurally prevents an agent from ever seeing/writing a credential. No harness surveyed has a dedicated, secret-typed routing lane distinct from its general approval mechanism. | **Keep building — closest is a generic approval pause, not a secret-typed lane.** |
| **4. Durable task ledger** | **Gas Town provides this, and provides it better than a hand-rolled version would**: "convoys" (`gt convoy create/list/show/add`) plus "beads" issue tracking are a first-class, persistent work-tracking model with OTEL-native event emission or ledger state, built specifically so agents don't lose context on restart. It is MIT-licensed and mature. The catch: it is coupled to Gas Town's own tmux/Go runtime and its own agent-provider capability matrix, which — as of this research — **does not list Antigravity/`agy`** either, so adopting it outright would not close the `agy` integration gap, only the ledger gap. | **Candidate to stop hand-building** — evaluate adopting Gas Town's convoy/bead model (or its ideas) instead of the hand-rolled ledger, but it does not solve execution-lane coverage for `agy`. |

**Honest recommendation implied by the evidence**: the task ledger (#4) is the one primitive where adopting existing, better-built infrastructure (Gas Town) is defensible today. The other three primitives — verifiable schema envelope, mandatory hard-stop declaration, and a structurally separate secrets lane — remain uniquely `lucind-ai`'s and were not found, even partially, in any of the eight-plus harnesses examined.

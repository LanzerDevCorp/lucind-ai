Problem

Deps has ~25 function-valued fields — effectively every side effect the whole system performs, hidden behind nothing. Every test that exercises Integrate, driveAttemptFromLeased, or the overlap gate fakes CombineTree, RunChecks, and PromoteCAS completely. The real composition — bisection driving real git merge --no-ff and real CAS — is wired exactly once, at cli.go, and never tested.

Solution

Group the 25 fields into a few deep seams by responsibility — a Workspace seam (worktree/combine/checks), a Promotion seam (CAS/target), a Gate seam (overlap/reconcile) — each with one real adapter and one test adapter, so two real adapters exist for at least one seam and the hypothetical/real distinction stops being guesswork.

  • ✓ Forces the missing real-composition test into existence
  • ✓ Also closes finding 6 (bisect only proven against fakes)
  • ✓ 25-field threading shrinks to 3 seams at every call site

Problem

"What happens when integration fails" bifurcates on hidden context (legacy vs. feature batch), and each path independently reimplements revert semantics and IntegrateReport construction over the same internal/integrate git primitives underneath.

Solution

Keep bisection as a real strategy difference, but make the dispatch explicit at one seam, and factor the shared combine → check → build-report → revert-or-promote scaffolding so the two paths differ only in bisection strategy, not in bookkeeping.

  • ✓ One place answers "how does failure reporting work"
  • ✓ Bisection becomes a swappable seam, not a forked codepath

5. Unify the combine → check → re-validate → CAS-promote protocol

Worth exploring duplication

internal/integrate/candidate.go:48–275 · internal/run/attempt.go:376–570

Before — two copies

ResolveAndPromoteCandidate
validate → worktree → combine → checks → re-validate → CAS
driveAttemptFromLeased + performCASPromotion
validate → worktree → combine → checks → re-validate → CAS

After — one protocol

fail-closed protocol
(validate → combine → checks →
re-validate → CAS)
parameterized by: ref source, lease vs. reconcile context

Problem

Both functions independently implement the same fail-closed sequence — pre-flight validate, worktree, combine, mandatory checks, re-validate both refs immediately before CAS to close the TOCTOU window, then promote. Deletion test: removing either and reusing the other fails without a rewrite — a correctness fix to the staleness re-check has to be found and applied twice by inspection, not by the compiler.

Solution

Extract the shared protocol as one deep module parameterized by what actually varies (ref sources, lease vs. reconcile context), so both callers configure the same implementation.

  • ✓ TOCTOU-window fix lands once, not twice
  • ✓ Passes the deletion test after the change: deleting one caller stops breaking the other
Checked, not flagged: parseDiffNameStatusZ / parseLSFilesZ (internal/run/gitpaths.go) look like pure helpers extracted purely for testability, but both the parsing edge cases and the real git-backed caller (enforceAllowedPaths) are exercised directly — this one passes the deletion test cleanly and isn't a candidate.

Top recommendation

Start with #1, collapsing Deps. It's the root cause behind the biggest coverage gap in the package — every composed behavior in internal/run is currently proven only against fakes — and fixing it also closes finding 6 (bisection's real-git behavior) for free. #3 (ledger.DB()) is the cheapest independent win and can land in parallel. #2, #4, and #5 all get easier to see clearly once #1 forces the real seams into existence.
